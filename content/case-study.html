Voice assistants in cars have learned a new trick: they can open a web page. Ask one to open a site and the browser on the center screen loads it. That's all most of them can do with the browser right now. They can't click, scroll, or fill in forms. We wanted to see what you could build if a single URL was the only control you had.

The result is Voiceboard, a set of games the assistant hosts by voice while the screen keeps score. It runs as a WordPress plugin on voiceboard.wpengine.com. Below is how it works and why WordPress turned out to be a good fit, followed by an honest list of what isn't built yet.

The idea: one URL per screen

The assistant is the host. It asks questions out loud, listens to answers, decides who was right, and keeps the game moving. Whenever the screen should change, it opens a new URL, and the page draws whatever the query string describes. A trivia question looks like this:

/board/?g=trivia&st=ask&t=Space&n=3&of=10
  &q=Which+planet+has+the+most+known+moons%3F
  &c=Jupiter|Saturn|Uranus|Neptune&p=Joe:200,Sam:100&timer=15

That URL gives you the question, four lettered choices, a progress label, both players' scores, and a 15-second countdown ring that runs down on its own. The reveal is the same URL with st=reveal&a=B&r=Sam, which turns Saturn green and announces who got it. Each link below is one complete screen, exactly as an assistant would open it:

Why the browser is enough

There's no app to install, no account, and no pairing step. Any screen with a browser can be the game board, and any assistant that can open a link can host. The board is a few small JavaScript modules and a stylesheet with no build step. Because every screen is fully described by its URL, a reload never loses anything and a link you share shows exactly what the player saw.

Assistants also write messy URLs, so the page is forgiving on purpose. It decodes values that were encoded twice, accepts an answer as B, 2, or Saturn, turns bad scores into zero, and infers the screen when st is missing. An unknown game opens the home screen instead of an error.

Teaching the assistant the rules

Nobody should have to read a prompt aloud before a road trip. The rules for hosting live in one file, llms.txt, and the plugin publishes it wherever an assistant might look. It's served at /llms.txt, which is becoming the usual place for AI-readable site instructions. It's also embedded in the board page's HTML, where it's hidden once the board renders but visible to tools that fetch pages without running JavaScript. In both places the plugin fills in the site's own board URL, using whichever domain the visitor typed.

The home page redirects to the board and keeps any game parameters. So the whole instruction for a person is one sentence: "Open voiceboard.wpengine.com and host trivia." The board shows that sentence on screen too, built from whatever domain it's running on.

Four places to keep state

Deciding where each piece of data lives did most of the design work. There are four stores, and each one exists because the others can't do its job.

For playing, the first two are enough. The URL draws the screen, and localStorage remembers the roster, so after the first question the assistant only sends changes like add=Sam:100. Reopening the same URL never applies a change twice. WordPress storage is for what a single browser can't do: give the assistant a record of the game it can read back, and give us a log of the URLs assistants really send. Presence answers one narrower question, which is who's playing right now.

Touch and voice have separate jobs

The screen is a touchscreen, so we had to decide what tapping does. The rule is that touch never changes game state. Passengers can browse games from the sidebar, switch between the light theme and the Cyber theme, or go fullscreen, which browsers only allow after a tap. Questions, answers, scores, timers, and effects belong to the assistant. Scoring follows the host's judgment, and the next URL always wins, so the assistant and the screen can't disagree. Tap-to-answer is planned, but only after there's a way to get those taps back to the assistant.

Why WordPress

A car game board isn't a typical WordPress project, yet every server-side piece it needs is something WordPress already provides. Hooks, custom post types, post meta, WP-Cron, and the REST API have run in production for years. Presence and Abilities are newer, and they build on the same structure.

  • The plugin handles /board/, /llms.txt, and the home redirect on the parse_request hook, before WordPress runs its main query. Board parameters like p= and w=, which WordPress would normally read as a post ID and a week number, are never misread. There are no rewrite rules to flush.
  • Sessions are posts. A game session is a document with a title (its code), a body (the transcript), and metadata (the latest scores and parsing diagnostics). That's exactly what a post is. A voiceboard_session custom post type gets admin list screens, capabilities, export, and the REST API without new tables.
  • WP-Cron prunes sessions older than 30 days.
  • The board reports each page view to a small REST endpoint, and an assistant that can read URLs fetches a plain-text transcript of players, scores, and questions already asked.
  • The Presence API feature plugin keeps short-lived "who's here" entries in its own wp_presence table with a TTL. Each car appears in a session room under a client ID like voiceboard-<carId>, and an entry that isn't refreshed simply expires. Presence is optional; without it you lose "who's online now" and nothing else.
  • The Abilities API has been in core since 6.9, and this site runs 7.1. Registering abilities such as voiceboard/add-score and voiceboard/get-transcript, then exposing them through the MCP Adapter, lets assistants that support tool calling run a game without building URLs.

Deploying is ordinary WordPress too. The plugin works the moment it's activated, with one optional setting under Settings → Reading that moves the board to the site root. It runs on a managed WordPress host with page caching. Because every state lives in the query string, the board's HTML is a static shell that caches well.

Three levels of assistant

Assistants differ a lot in what they can do, so the design adds features in layers. Nothing at one level depends on the next.

  1. An assistant that can only open a URL gets the full game on screen. This is what in-car assistants can do today.
  2. An assistant that can also read a URL gets the transcript, so it never has to keep a running tally in its head.
  3. An assistant that can call tools over MCP gets structured abilities, and the board follows along by polling its session.

Free games for anyone with a voice and a screen

Anyone with a voice assistant that can hold a conversation and a screen with a browser now has a game show host and several games at no cost. Grok, Gemini, Siri, Alexa, and ChatGPT are all examples; the board doesn't care which one opens the URL.

Playing is hands-free. The assistant reads the questions, so you don't need to read anything beyond a glance at the scores. That opens it up to kids who can't read fluently yet, to older adults who'd rather talk than tap, and to people with limited mobility. The board uses large type, follows the device's light or dark setting, announces changes to screen readers, marks the countdown as a timer, and skips the confetti when reduced motion is turned on.

How we build it

A Playwright suite covers the games, the parsing edge cases, the remembered roster, the effects, and the plugin's routes. It runs twice: once against the static files and once against the plugin inside WordPress Playground, a real WordPress install that needs no Docker or database setup. Every push to the main branch runs the suite. Only when it passes are the plugin files synced to the live site and the caches flushed. Release Please turns conventional commit messages into a versioned release with a changelog and a downloadable plugin zip.

Where it stands

Shipped: the URL-driven games (trivia and a Jeopardy-style board), the themes, the timer and confetti effects, the localStorage roster and Hall of Fame, the WordPress plugin, llms.txt, the home redirect, and continuous deployment.

Designed but not built yet: sessions and transcripts, the URL log, presence, and the abilities for MCP. We also haven't tested with real assistants in a car. Whether an in-car assistant reads the instructions on its own, how reliably it writes these URLs over a long game, and whether reopening a URL reuses the same browser tab are open questions. The URL log is meant to answer them, and we'll write up what it shows.

After that, we want to add more games (road trip bingo, a drawing game, a blur-to-reveal round), tap-to-answer once taps can reach the assistant, and an abilities-first mode for assistants that speak MCP.

The source is on GitHub. The design is inspired by in-car interfaces; the project isn't affiliated with any carmaker.
